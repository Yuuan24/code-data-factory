# Feature Specification: Code Data Factory

**Feature Branch**: 未创建（项目未配置分支创建钩子）

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "设计一个约 12 周的大模型数据工程项目，覆盖代码训练数据生成与
治理、执行验证、质量和多样性控制、评测反馈闭环、数据敏感性和数据价值归因，并以分级证据
量化数据对模型能力与泛化能力的贡献；引入 Ray 展示可核验的大规模数据处理实践。"

**Reference Context**: 本规格聚焦可在有界项目中实证的数据生产、治理、质量、评测和价值度量
要求，不将无界采集、组织级基础设施或通用训练平台纳入范围。

## User Scenarios & Testing *(mandatory)*

优先级（Priority，P）使用 P1、P2、P3 表示；P1 为最高优先级。每个场景都可以使用有界输入和
已准备好的依赖独立验收，不要求先完成其他场景的全部实现。

### User Story 1 - 构建可追踪的代码数据版本 (Priority: P1)

作为个人项目开发者，我希望从有界代码来源和明确的生成任务构建训练数据版本，使每条样本的
来源、处理、质量、去重、选择和归属都可以追踪，并能展示数据工程价值而非只有文件数量。

**Why this priority**: 可治理、可复现的数据版本是执行验证、评测闭环和价值归因的共同基础。

**Independent Test**: 使用一个固定的小型代码来源和一组生成任务构建数据版本，随机抽取接受、
拒绝和修复样本，确认每条样本都能追溯到来源、处理动作、质量证据、数据切分和版本清单。

**Acceptance Scenarios**:

1. **Given** 已冻结的代码来源和生成任务，**When** 用户构建候选数据，**Then** 每条候选样本
   都有稳定标识、来源记录和完整处理轨迹。
2. **Given** 已声明的质量与多样性目标，**When** 用户发布数据版本，**Then** 系统同时产出
   不可变清单、切分记录、处理前后分布和数据卡。
3. **Given** 来源许可不明确、包含明显密钥或个人可识别信息的样本，**When** 治理检查运行，
   **Then** 样本被隔离或拒绝，原因和后续动作被记录。
4. **Given** 相同的冻结输入、业务算子和配置，**When** 用户分别以本地模式和 Ray Data 分布式模式
   构建数据，**Then** 两次运行产生相同的接受/拒绝决策和逻辑内容哈希；物理分片与行顺序差异不被
   误报为数据语义变化。
5. **Given** 明确标为仅基准测试且与训练/评测隔离的固定规模输入，**When** 用户在 1、2、4 个
   Linux worker node（工作节点）上运行同一 Ray Data 流水线，**Then** 系统保存实际拓扑、每阶段
   吞吐、资源、shuffle（重分布）、spill（溢写）、重试、失败、成本和输出哈希；缺少真实多节点
   运行时不得发布分布式扩展成果。

### User Story 2 - 获得可信的代码执行证据 (Priority: P1)

作为个人项目开发者，我希望区分静态检查和真实安全执行，并保存编译、测试、失败与重复运行证据，
使“代码可运行”这一结论可以被独立核验。

**Why this priority**: 代码训练数据的关键差异在于能否以真实执行结果验证正确性，同时不把不可信
代码带到无隔离环境中运行。

**Independent Test**: 准备正确、错误、超时和结果不稳定的代码样本；在安全执行环境可用与不可用
两种条件下运行验证，确认样本只获得其实际满足的证据层级，并保留全部原始结果。

**Acceptance Scenarios**:

1. **Given** 满足隔离和资源限制的执行环境，**When** 代码完成编译和重复测试，**Then** 系统
   保存环境身份、输入、原始日志、退出状态、资源使用和每次运行结果。
2. **Given** 安全执行环境不可用，**When** 用户请求执行验证，**Then** 系统拒绝把本地或模拟
   结果升级为安全执行验证，并将结论标为软件级验证或尚未验证。
3. **Given** 多次执行结果不一致，**When** 系统汇总验证状态，**Then** 样本被标记为不稳定，
   不得进入已执行验证的数据层。

### User Story 3 - 用评测短板驱动数据迭代 (Priority: P2)

作为个人项目开发者，我希望把模型评测中的错误和能力短板映射到数据切片，并生成、修复或重选
专项数据，使下一版数据能够明确回应上一轮评测发现。

**Why this priority**: 只有评测结果实际改变下一轮数据决策，项目才形成数据到模型再回到数据的
闭环，而不是单次清洗流水线。

**Independent Test**: 使用一份包含逐题结果和错误类别的评测产物，完成短板识别、数据切片定位、
专项数据动作和新版本发布，确认每项动作都能回溯到原始评测发现。

**Acceptance Scenarios**:

1. **Given** 带有逐项结果的模型评测，**When** 用户分析失败模式，**Then** 系统形成可审计的
   评测发现，并关联受影响能力、数据切片和证据。
2. **Given** 已确认的评测短板，**When** 用户创建专项数据版本，**Then** 新增、修复、降权、
   删除或复核动作都关联短板、决策理由和复验计划。
3. **Given** 新一轮评测已完成，**When** 用户关闭本轮反馈，**Then** 系统记录短板是否改善、
   是否产生回退，以及下一轮数据策略。

### User Story 4 - 量化数据对模型能力的贡献 (Priority: P2)

作为个人项目开发者，我希望用固定训练预算的处理组和公平对照组测量数据价值，同时观察模型在
受约束数据工程任务中一次生成 Python 转换或修复程序的端到端任务成功率，以及未见任务/数据集
泛化、通用能力回退和安全表现，使数据贡献结论具有可复现实验依据。代码文本相似度和通用代码
能力不作为最终目标。

**Why this priority**: 量化数据价值是本项目区别于普通数据清洗项目的核心结果，但不能以预期
收益代替真实训练。

**Independent Test**: 在真实训练环境可用时，使用冻结的数据版本、基础模型和分析计划运行一组
处理组与对照组训练并复评；环境不可用时，验证系统只生成软件级实验计划和产物检查，不发布
模型提升结论。

**Acceptance Scenarios**:

1. **Given** 已冻结的实验计划和真实训练环境，**When** 处理组与对照组完成训练和评测，
   **Then** 两组训练预算及非数据条件一致，差异、波动、成本和原始评测结果全部保存。
2. **Given** 实验结果为无提升、负提升或存在能力回退，**When** 用户生成价值报告，**Then**
   结果按实际数值发布，不被删除或改写为正向收益。
3. **Given** 缺少真实训练环境，**When** 用户查看模型贡献报告，**Then** 所有相关结论明确标为
   软件级验证或尚未验证，且报告中不存在已实现模型提升的陈述。

### User Story 5 - 独立审阅和复现实验证据 (Priority: P3)

希望从任一展示结论快速定位数据、处理、执行、训练和评测产物，
并按说明复现至少一个代表性流程，以判断项目声明是否真实可信。

**Why this priority**: 项目必须让外部读者核验证据，不能依赖作者口头补充或只展示最终图表。

**Independent Test**: 选择一条软件能力结论、一条安全执行结论和一条模型贡献结论或其降级记录，
按照证据索引逐项检查来源、层级、原始产物和重跑说明。

**Acceptance Scenarios**:

1. **Given** 任一已发布结论，**When** 评审者查看证据索引，**Then** 可以定位其证据层级、输入、
   运行记录、原始产物、限制和复现入口。
2. **Given** 一项依赖外部调研的大模型研究结论或方法方案，**When** 评审者核查引用，**Then**
   每个来源都满足 FR-005 的时效、版本和替代检查要求。
3. **Given** 评审者选择一个代表性数据版本，**When** 按重跑说明复现，**Then** 输出哈希一致，
   或差异处于事先声明并解释的容差内。

### Edge Cases

- 来源在构建后被删除、修改许可或撤销授权时，已发布数据版本如何定位和执行删除或隔离？
- 同一样本经过不同来源或生成路径进入候选池时，如何保留来源关系并避免重复计入？
- 去重提高质量但显著降低某些能力切片覆盖时，如何暴露而不是隐藏该取舍？
- 质量评分较高但安全执行失败时，样本如何降级并阻止进入已验证数据层？
- 编译成功但测试不充分，或生成测试无法识别错误实现时，如何避免错误晋级？
- 安全执行发生超时、资源耗尽、网络访问尝试或结果不稳定时，如何记录并分类？
- 训练中断、部分完成或处理组与对照组预算不一致时，如何阻止因果结论发布？
- 评测集与训练数据发生直接或近似污染时，如何隔离受影响指标并重新评测？
- 目标代码能力提高但未见代码场景、通用能力或安全能力回退时，如何呈现净贡献？
- 生成代码能够通过局部单元测试，但最终数据产物的 schema（模式）、数据质量断言或业务不变量
  不满足时，如何保证任务仍判为失败？
- 评测没有发现稳定短板或专项数据没有改善结果时，闭环如何保留无效尝试？
- 大模型研究资料不满足 FR-005 时，如何阻止其支撑
  当前研究结论或方法方案，同时不误伤仍在维护的成熟通用组件？
- 没有真实训练或安全执行环境时，如何保证所有页面和报告保持软件级验证边界？
- Ray 的并行分片与调度顺序发生变化时，如何保证业务决策、逻辑内容哈希和数据谱系保持一致？
- Ray worker 在输出提交前后失败并触发重试时，如何避免重复写入、部分发布或把恢复后的成功隐藏为
  “从未失败”？

## Requirements *(mandatory)*

### Functional Requirements

需求编号中的 `FR` 表示功能需求（functional requirement）。

#### Scope and Positioning

- **FR-001**: 项目必须在约 12 周的有界范围内，为代码训练数据生成与治理、执行验证、质量控制、
  多样性控制、评测反馈、数据敏感性和数据价值归因分别提供可演示产物。
- **FR-002**: 首个可交付版本必须限定一种主编程语言、有界数据来源和代码及必要文本数据；
  新增语言或无界来源必须作为后续独立范围处理。
- **FR-003**: 模型训练必须仅作为数据价值的下游测量手段，项目不得把通用训练框架或基础模型
  研发列为交付目标；正式归因只使用成熟开源组件完成最小监督微调，项目自有代码不得实现优化器、
  分布式训练调度器或通用 rollout（策略采样）平台。RL 兼容产物不得自动扩展为正式 RL 训练。
- **FR-004**: 项目不得包含图像、音频、视频等多模态处理、互联网级采集、分布式爬虫、
  拍字节（petabyte，PB）或艾字节（exabyte，EB）级基础设施、数据库内核或组织级平台建设。
- **FR-005**: 支持当前大模型研究结论或方法方案的外部资料必须满足宪章规定的 `2026-04-01`
  最早日期、原始日期验证、版本检查和未被更新资料取代的要求；通用组件选型不受该日期门槛
  约束，其当前维护状态、版本、许可、兼容性、安全性和项目适配性由规划阶段审查。

#### Data Generation and Governance

- **FR-006**: 用户必须能够从冻结的来源快照和版本化生成任务构建候选代码数据。
- **FR-007**: 每条候选样本必须具有稳定标识，并记录来源、许可、真实或合成属性、生成上下文、
  父样本及所属数据版本。
- **FR-008**: 每次过滤、去重、修复、重新生成、降权、删除、接受或人工复核都必须记录动作、
  原因、输入证据、执行者和时间。
- **FR-009**: 每个已发布数据版本必须不可变，并包含内容哈希、样本清单、训练与评测切分、
  版本关系和可重建入口。
- **FR-010**: 治理检查必须识别并隔离许可不合格、明显密钥、个人可识别信息和已知评测污染；
  未通过检查的样本不得静默进入训练数据。
- **FR-011**: 删除、更正或许可撤销必须形成台账，并可定位所有受影响数据版本、实验和结论。
- **FR-012**: 每个数据版本必须提供数据卡，说明来源、用途、限制、质量、多样性、敏感风险、
  已知缺口和允许的证据层级。

#### Execution Validation

- **FR-013**: 每条代码样本必须区分未验证、静态验证、安全执行验证和验证失败状态。
- **FR-014**: 静态验证必须保存所运行检查、输入版本、结果和失败原因，但不得被描述为代码已
  在安全环境中真实运行。
- **FR-015**: 安全执行开始前必须验证环境具备隔离、非特权身份、网络限制、只读基础环境、
  时间和资源上限以及可审计版本；任一条件缺失时必须拒绝晋级。
- **FR-016**: 安全执行必须保存每次编译和测试的原始输出、退出状态、耗时、资源结果及重复运行
  一致性，不得只保留最终布尔结果。
- **FR-017**: 当验证测试由模型生成时，系统必须保存测试能够拒绝错误实现的独立证据；缺少该
  证据时不得把样本晋级为已充分验证。
- **FR-017a**: 若发布 RL-ready（可供强化学习消费）数据，数据单元必须保存问题、候选输出、最终
  数据产物、验证器及版本、原始执行结果、奖励分量、汇总奖励和重放入口；奖励不可计算、重复
  执行不一致或验证强度不足时必须拒绝 RL-ready 标记。该标记不证明真实 RL 已发生。
- **FR-018**: 安全执行环境不可用时，系统必须失败关闭，并将相关能力和结论标为软件级验证或
  尚未验证。

#### Quality, Diversity, and Data Sensitivity

- **FR-019**: 每次数据构建必须在运行前声明质量维度、门槛、失败处理和报告口径。
- **FR-020**: 数据版本必须报告处理前后的质量、样本数、词元数、重复、验证结果和异常分布；
  RL-ready 数据还必须报告唯一可验证任务产出率、奖励可计算率、奖励重放不一致率、验证器变异
  检出率、切片覆盖保留率以及每千个唯一可验证任务成本。
- **FR-021**: 数据版本必须按预先声明的技能、来源、真实或合成、难度、长度、生成路径、质量
  层级及其他相关切片报告覆盖和比例变化。
- **FR-022**: 系统必须检测训练数据内部重复以及训练数据与评测数据之间的直接或近似污染，
  并隔离受影响样本和指标。
- **FR-023**: 数据敏感性分析必须形成“发现、解释、决策、复验”记录，使每项数据动作都能
  关联切片证据和后续结果。
- **FR-024**: 单一综合质量分数不得作为接受样本、证明多样性或证明模型价值的唯一依据。

#### Evaluation Feedback Loop

- **FR-025**: 系统必须接收模型评测的逐项结果、能力标签、错误类别和评测版本，并保持原始结果。
- **FR-026**: 用户必须能够把评测失败模式映射到数据切片，形成带证据、优先级和复验计划的
  数据缺口。
- **FR-027**: 专项数据版本中的新增、修复、重选、降权或删除动作必须关联其评测发现，并在下一
  轮评测后记录改善、无变化或回退。
- **FR-027a**: 正式监督微调处理组和对照组必须从同一合格任务池构建并匹配来源、任务类型、难度、
  长度、测试强度和基线模型成功率；两组只允许在预先声明的数据选择策略上存在差异。

#### Data Value Attribution

- **FR-028**: 每项数据价值实验必须在查看处理组结果前冻结假设、处理组、对照组、训练预算、
  主次指标、重复次数、随机种子、训练方法选择记录和判定规则。训练方法可以是全参数微调、低秩
  适配（Low-Rank Adaptation，LoRA）或量化低秩适配（Quantized LoRA，QLoRA），但正式对比只能
  冻结一种，且不得为了训练方法比较扩大第一版实验矩阵。
- **FR-029**: 同一数据归因实验中的处理组和对照组必须保持基础模型、初始权重、训练方法、
  计划和实测有效训练词元、优化步数、其他计算预算、优化设置、曝光策略、数据验证器版本、解码
  设置和评测版本一致；任一公平性门禁失败时不得发布因果提升结论。
- **FR-030**: 处理组与对照组之间只能保留预先声明的目标数据差异；无法隔离时必须标记为
  相关性或探索性结果，不得发布因果结论。
- **FR-031**: 价值评测必须以受约束数据工程任务的一次生成端到端成功率为主指标；只有生成程序
  产生的最终数据产物、隐藏数据质量断言和任务约束同时通过才计为成功。评测还必须覆盖修复任务、
  未见任务/数据集泛化、推理成本、通用能力回退和安全表现，不得用代码文本相似度、局部单元测试、
  训练 loss、可选 RL 奖励或最有利的单一指标替代隔离评测。
- **FR-031a**: 冻结的评测套件必须采用“当前外部 benchmark 锚点 + 项目数据工程扩展”的分层设计：
  外部层复用 2026-04-01 之后的前沿模型官方报告或 benchmark 官方资料仍在使用的任务、执行协议和
  标准指标，以提供可比性与通用回退护栏；项目层评测最终数据产物、隐藏数据质量/业务不变量以及
  任务模板、来源仓库、输入数据集不相交泛化。两层必须分别报告，禁止合成一个自定义总分；外部
  benchmark 的许可、版本、执行镜像、样本子集、污染检查和对原协议的偏离必须被记录。
- **FR-032**: 每项实验必须保存原始训练记录、模型产物、逐项评测结果、重复实验波动、计算成本、
  资金成本、失败运行、负结果和无提升结果。
- **FR-033**: 没有真实训练及公平对照产物时，系统不得生成“数据已经提升模型”的结论，相关
  报告必须标为软件级验证或尚未验证。

#### Evidence and Reproduction

- **FR-034**: 每条发布结论必须具有稳定标识和明确证据层级，并链接到数据、执行、训练、评测、
  外部资料、限制和重跑入口。
- **FR-035**: 系统必须同时提供便于评审者阅读的证据报告和便于自动核验的证据清单，两者不得
  维护相互冲突的事实状态。
- **FR-036**: 用户必须能够从冻结输入重建至少一个代表性数据版本，并在真实依赖可用时重跑其
  对应执行、训练和评测流程。
- **FR-037**: 软件完成、测试通过、服务启动、数据规模、外部研究收益或预测收益不得被自动转换
  为安全执行或模型提升结论。
- **FR-038**: 所有预先登记的正向、负向、无变化、失败和中止结果必须保留并在证据报告中可访问。

#### Distributed Data Processing

- **FR-039**: 数据构建必须提供 Ray Data 分布式执行模式，并与小规模本地模式复用同一套业务算子、
  Pydantic/Arrow 契约和稳定样本标识；不得维护两套语义不同的过滤、去重或选择规则。
- **FR-040**: 每次 Ray 运行必须保存 Ray 版本和提交、任务标识、实际物理节点与 worker 进程数量、
  每节点资源、输入输出哈希、算子级吞吐与耗时、峰值内存、对象存储 spill、shuffle、重试、失败和
  实付或可核验成本；不支持的指标必须明确为不可用，不得填零。
- **FR-041**: 规模实验必须在运行前冻结同一输入、同一算子图、同构 worker 资源、重复次数和指标
  口径，通过节点互达、实际 Ray 任务分布和共享存储读写探针，并分别运行 1、2、4 个工作节点；
  单机多进程或仅可 SSH 只能证明部分软件/网络兼容性，不能替代真实多节点证据。
- **FR-042**: 为规模实验确定性扩增的数据必须标记 `BENCHMARK_ONLY`，与训练、开发、测试和模型
  归因数据物理及逻辑隔离，并被所有数据发布和训练入口失败关闭地拒绝。
- **FR-043**: 每个用户故事 checkpoint 必须复核并更新 `docs/evidence-journal.md`：在难点发现、
  作出选择和取得真实结果时分别记录问题机制、现实候选方案、最终取舍、未解决限制、验证方法和
  证据链接；“采用某组件”或“修改某参数”不得单独作为解决方案。没有新增非平凡难点时必须保存
  一条关联任务和产物的检查点回执，不得虚构亮点，也不得推迟到最终阶段凭记忆补写。

### Key Entities *(include if feature involves data)*

- **Source Snapshot**: 一组在特定版本冻结的代码或文本来源，包含来源身份、许可、内容哈希和
  获取时间。
- **Data Sample**: 候选、接受、拒绝或修复的最小数据单元，具有稳定标识、内容、来源关系、
  数据切片和当前证据状态。
- **Transformation Record**: 对样本执行的生成、解析、过滤、去重、修复、选择、删除或复核动作，
  包含原因、输入证据和结果。
- **Dataset Version**: 不可变的样本集合及其清单、切分、哈希、父版本、质量、多样性和数据卡。
- **Data Slice**: 按技能、来源、难度、生成路径、质量或其他属性定义的可分析样本集合。
- **Verification Evidence**: 静态检查或安全执行的环境、输入、日志、退出状态、资源结果、重复
  运行和证据层级。
- **Evaluation Finding**: 从逐项评测结果归纳的能力短板、错误模式或回退，并关联数据切片和
  证据。
- **Experiment Plan**: 在查看处理组结果前冻结的数据假设、处理组、对照组、训练预算、指标、
  重复和判定规则。
- **Training Run**: 一次实际模型参数更新运行，关联数据版本、模型初始状态、配置、种子、日志、
  成本和模型产物。
- **Evaluation Run**: 对一个模型产物执行的版本化评测，包含逐项预测、得分、能力维度和汇总。
- **Published Claim**: 面向项目报告发布的精确结论，关联证据层级、全部支持产物、限制、
  相反证据和复现入口。
- **Data Pipeline Run**: 一次本地或 Ray Data 数据流水线执行，记录冻结输入、算子图、运行拓扑、
  算子级资源与性能、失败恢复、成本、输出逻辑哈希和证据层级。
- **Scale Benchmark**: 对同一 `BENCHMARK_ONLY` 工作负载进行的 1/2/4 工作节点重复运行集合，包含
  扩展效率、稳定性、瓶颈解释和允许发布的精确结论边界。

### Scope Boundaries

- 规格仅覆盖个人可在约 12 周内完成和证明的代码及必要文本数据工作。
- 不要求达到生产级可用性、互联网规模、组织级多租户能力或生产服务等级目标；只要求 SC-014
  定义的有界 Ray 规模实测及诚实结果。
- 不要求实验产生正向模型提升；准确量化零收益、负收益和泛化回退同样满足价值归因目标。
- 不允许使用未验证的外部论文收益、模拟训练结果或计划指标替代本项目真实结果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

成功标准编号中的 `SC` 表示成功标准（success criterion）。

- **SC-001**: 项目结束时，七项目标能力中的每一项至少有一个可访问产物，并明确标注为软件级、
  安全执行级、训练证据级或尚未验证。
- **SC-002**: 已发布数据版本中的 100% 样本都能追踪到来源、处理动作、切片、数据切分和验证
  状态；无法追踪的样本数量为零。
- **SC-003**: 100% 已发布数据版本都包含不可变清单、内容哈希、数据卡以及处理前后的质量与
  多样性报告；RL-ready 数据版本还包含奖励可计算率、奖励重放稳定性、验证器区分度和单位数据成本。
- **SC-004**: 100% 标记为安全执行验证的样本都具有符合要求的隔离环境证据和原始运行记录；
  不具备该证据却被标记为安全执行验证的样本数量为零。
- **SC-005**: 至少完成一条从逐项评测发现到专项数据动作、下一数据版本和复评结果的完整可追踪
  闭环；若缺少真实评测依赖，必须明确标为软件级闭环演示而非模型收益证据。
- **SC-006**: 真实训练环境可用时，至少完成一项固定预算的处理组与对照组训练实验；100% 模型
  提升结论都具有完全一致的已声明训练预算、端到端谱系、原始评测结果、重复实验结果和限制
  说明。
- **SC-007**: 如果真实训练环境不可用，已发布模型提升结论数量必须为零，所有相关输出都必须
  标记为软件级验证或尚未验证。
- **SC-008**: 每份训练证据级报告都分别展示外部 benchmark 指标与协议偏离，以及项目套件的
  `ArtifactPass@1`、`RepairPass@1`、`HeldOutArtifactPass@1`、推理成本和安全表现；不同层不
  合成总分，且正向、负向和无变化结果的保留率均为 100%。
- **SC-009**: 独立评审者能够仅依靠仓库内说明，从任一发布结论定位全部支持证据，不需要作者
  口头补充未记录的步骤。
- **SC-010**: 独立评审者能够从冻结输入复现至少一个代表性数据版本；输出哈希必须一致，或所有
  差异均处于运行前声明并解释的容差内。
- **SC-011**: 100% 支持当前大模型研究结论或方法方案的外部资料都满足 FR-005；组件选型记录
  不按发布日期验收。
- **SC-012**: 最终项目报告和公开文档中，超出范围的多模态、互联网规模、拍字节或艾字节基础
  设施、数据库内核及组织级平台成果声明数量为零。
- **SC-013**: 同一冻结输入的本地模式和 Ray Data 模式产生相同逻辑内容哈希、样本决策和谱系的
  比例为 100%；任一不一致都会阻止数据版本发布。
- **SC-014**: 至少完成同一冻结规模工作负载在 1、2、4 个独立 Linux 工作节点上的各 5 次实测，
  并发布吞吐、墙钟时间、扩展效率、资源峰值、spill、shuffle、失败恢复与成本产物。若未完成真实
  多节点运行，本标准必须标为未满足，最终材料中的分布式扩展成果声明数量必须为零。
- **SC-015**: 100% 已完成的用户故事 checkpoint 都具有同期产生的难点更新或检查点回执；所有
  `RESOLVED` 难点都包含至少一个被放弃方案、可解释的取舍、实际验证结果和证据链接，所有
  `VERIFIED` 亮点都能反向关联到对应难点及其证据层级。

## Assumptions

- 主要使用者是完成项目的个人数据工程师；。
- 约 12 周是项目范围和优先级约束，具体阶段、技术选择和逐周排期由后续计划确定。
- 首个版本只需选择一种具有可执行测试生态的主编程语言，并使用有界、版本可冻结且许可清晰的
  公开来源以及可审计的合成数据。
- 项目可以依赖外部模型服务、训练资源和安全执行环境，但这些依赖不被假定为始终可用；每项
  结果必须按实际可用环境确定证据层级。
- 模型训练用于测量数据价值，不承担通用训练平台、基础模型研发或训练基础设施建设职责。
- 训练预算的绝对规模、具体对照配方、质量门槛和数据切片将在规划阶段冻结；本规格只规定它们
  必须公平、可审计、可复现且在查看结果前声明。
- 项目成功的含义是可信地测量并报告数据效果，而不是保证获得正向模型提升。
- 所有支持当前大模型研究结论或方法方案的引用都遵守宪章的资料时效要求；找不到合格资料时
  记录证据缺口，不降低日期标准。通用组件选型不适用该日期标准。
